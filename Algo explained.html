Position-Sizing Algorithm

The Masaniello Method

A build reference for the Masaniello staking algorithm — the exact formulas, data shapes, and source functions behind every stake, plan, and stop condition, in enough detail to reimplement it from scratch and verify the result against real numbers.

Notation, before anything else

One point of confusion up front: lowercase letters are live, shrinking values that count down as trades happen; the matching uppercase letter is the fixed number the session started with and never changes — n starts at N and counts down; N itself never moves. Every other symbol below is introduced properly where it first matters, but this is the one place all of them are in one list.

01

The core idea

The algorithm doesn't stake a fixed dollar amount, and it doesn't stake a fixed percentage. It stakes exactly the amount that makes one fact true: whichever k of your remaining n trades you happen to win, in whatever order, you land on the same final balance.

That's the whole method in one sentence. Win early and the stakes still ahead of you shrink, because you need fewer wins from fewer trades. Lose early and the next stake grows, because the same win count now has to come from a shorter runway. The table in the next section is what makes that adjustment exact instead of a rule of thumb.

Where this lives in the code

trade_manager/masaniello.py is a line-for-line port of a reference JavaScript implementation — the algorithm itself was never redesigned in the port, only translated from one language to another.

02

Building the table

Everything starts with build_table(n, q_avg), which fills a triangular grid t[n][k]: the multiplier your bankroll grows by if you land exactly k wins somewhere within the next n trades, at an average payout q_avg (a decimal — 0.90, not 90).

Two edges anchor the grid, and everything else is filled in between them by recursion:

The two anchors

t[n][0] = 1.0 // already hit your win target — nothing left to risk t[m][m] = (1 + q)^m // must win every single remaining trade

Everything in between

t[n][k] = ( t[n-1][k-1] · t[n-1][k] · (1 + q) ) ----------------------------------------- ( t[n-1][k-1] · q + t[n-1][k] )

Each cell is built from the two cells that could follow it — one trade win away (t[n-1][k-1]), one trade loss away (t[n-1][k]) — weighted so that a win and a loss on that next trade both land you back on the same table. It's the same recursive shape as Pascal's triangle; the payoff ratio is what bends it instead of the usual 1s.

trade_manager/masaniello.pyPython
def build_table(n: int, q_avg: float) -> list[list[float]]:
    # t[n][k]: growth multiplier for landing k wins within n trades, any order
    size = n + 1
    t = [[0.0] * size for _ in range(size)]

    for nn in range(size):
        t[nn][0] = 1.0                      # target already met

    for m in range(size):
        t[m][m] = (1 + q_avg) ** m          # must win every remaining trade

    for nn in range(1, size):
        for k in range(1, nn):              # kMax = nn-1 always, since nn <= n throughout
            a = t[nn - 1][k - 1]            # multiplier if this trade wins
            b = t[nn - 1][k]                # multiplier if this trade loses
            t[nn][k] = (a * b * (1 + q_avg)) / (a * q_avg + b)

    return t

Complexity is O(n²) — one nested loop over a triangular grid. Build once per session (whenever n or the average payout assumption changes), then reuse the same table for every stake in that session; there's no reason to rebuild it per trade.

03

Turning a cell into a stake

The table only holds multipliers. The actual dollar figure you see before each trade comes from stake_fraction(), which reads off this trade's slice of the table and converts it into a fraction of your current balance:

trade_manager/masaniello.pyPython
def stake_fraction(n, k, q_next, t, diagonal_mode, max_stake_percent) -> float:
    if k <= 0:
        return 0.0                          # already hit target win count
    if n <= k:                              # diagonal -- see §05
        if diagonal_mode == "capped":
            cap = max_stake_percent if isinstance(max_stake_percent, (int, float)) else 100
            return min(1.0, max(0.0, cap / 100))
        return 1.0                          # pure mode: stake it all
    a = t[n - 1][k - 1]
    b = t[n - 1][k]
    denom = a * q_next + b
    if denom <= 0:
        return 0.0
    return (b - a) / denom


def next_stake(current_capital, trades_remaining, wins_still_needed,
               q_next, t, diagonal_mode, max_stake_percent) -> float:
    frac = stake_fraction(trades_remaining, wins_still_needed, q_next,
                           t, diagonal_mode, max_stake_percent)
    return current_capital * frac

Notice the table itself is built once from your average assumed payout (q_avg), but every individual stake uses q_next — the real payout the broker is offering on this specific trade, which binary-options payouts shift on constantly. Average and actual can differ without needing to rebuild anything; only this last step reads the live number.

Why this distinction matters

If stakes were computed off the average instead, the tracked balance would quietly drift away from your real broker balance every time the offered payout moved even slightly from the average — exactly the kind of silent mismatch this method is built to avoid.

04

A worked session

$100 bankroll, 3 trades planned, 1 win needed, payout 100% flat — the exact case the algorithm's own test suite checks by hand.

Trade 1's stake comes straight from the grid above: t[2][0]=1.00, t[2][1]=1.33, so stake_fraction = (1.33 − 1.00) / (1.00×1 + 1.33) ≈ 1/7 — $14.29 of the $100 bankroll. What happens next branches on the result:

TradeStakeResultBalance after
1 of 3$14.29WIN$114.29

Path B — the win doesn't land until trade 3

Both paths land within a cent of the same $114.28–$114.29 — the one-cent gap is nothing but rounding drift across two different arithmetic paths, not a flaw. Trade a 2, then a 1, needed to win exactly once out of what's left each time; the stake grows precisely enough each step to keep that promise, right up to trade 3 becoming a must-win-it-all stake of the entire remaining balance.

05

The endgame trade

Whenever trades left equals wins still needed (n = k — the diagonal in the table), every remaining trade has to be a win. Call this Endgame handling, and it's the one place a caller decides how aggressive the method is allowed to get:

Mode: pure

Stakes 100% of current capital on the must-win trade — the original, textbook Masaniello method. A single loss here ends the session with nothing left. Highest possible ceiling, zero cushion.

Mode: capped

Caps the stake at Max stake % of current capital instead of going all-in. Trades a lower profit ceiling for keeping some capital if that last trade is lost.

This is exactly the choice in the worked example's trade 3: pure mode staked the full $57.14; capped mode at, say, 50% would have staked $28.57 and left the other half untouched either way.

07

Session lifecycle

Three operations mutate the session record above: recording a trade, checking whether it should end, and correcting a misrecorded result. All three live together because they share one rule — never trust a cached derived value; recompute it from the trade list every time.

Recording a trade

trade_manager/session.pyPython
def record_trade(session, result, q_next_pct, stake_used=None) -> dict | None:
    table = build_table(session["inputs"]["N"], session["inputs"]["avgPayoutPct"] / 100)
    suggested = round2(clamp(
        suggested_stake_for(session, table, q_next_pct), 0, session["currentCapital"]
    ))
    if stake_used is None or stake_used < 0:
        stake_used = suggested
    stake_used = round2(min(stake_used, session["currentCapital"]))  # never stake more than you have

    capital_after = (
        round2(session["currentCapital"] + stake_used * (q_next_pct / 100))
        if result == "win"
        else round2(session["currentCapital"] - stake_used)
    )

    session["trades"].append({
        "index": len(session["trades"]) + 1,
        "payoutPctUsed": q_next_pct,
        "stakeSuggested": suggested,
        "stakeUsed": stake_used,
        "result": result,
        "capitalAfter": capital_after,
    })

    session["currentCapital"] = capital_after
    session["tradesRemaining"] -= 1
    if result == "win":
        session["winsNeeded"] -= 1

    reason = check_end_conditions(session)
    return end_session(session, reason) if reason else None

Checking whether the session should end

Called after every recorded trade, always in this priority order — so two conditions that could both be true at once (say, balance hit $0 and the win target became impossible) are never reported as the wrong one:

  1. Target unreachable — tradesRemaining < winsNeeded. Losses so far have made the target mathematically impossible, regardless of balance.
  2. Target hit — winsNeeded == 0.
  3. Take Profit — only if its forceEnd flag isn't False.
  4. Stop Loss — only if its forceEnd flag isn't False.
  5. Trades exhausted — tradesRemaining == 0 without any of the above.
trade_manager/session.pyPython
def check_end_conditions(session) -> str | None:
    inputs = session["inputs"]
    c0 = inputs["bankroll"]
    current_capital = session["currentCapital"]

    if session["tradesRemaining"] < session["winsNeeded"]:
        return "target_unreachable"
    if session["winsNeeded"] == 0:
        return "target_hit"

    tp_amt = threshold_amount(c0, inputs["takeProfit"])
    if inputs["takeProfit"].get("forceEnd", True) is not False and current_capital - c0 >= tp_amt:
        return "take_profit"

    sl_amt = threshold_amount(c0, inputs["stopLoss"])
    if inputs["stopLoss"].get("forceEnd", True) is not False and c0 - current_capital >= sl_amt:
        return "stop_loss"

    if session["tradesRemaining"] == 0:
        return "trades_exhausted"
    return None

Correcting a misrecorded result

Only while status == "active" — a completed history record never needs to be un-archived. Editing one trade's result recomputes every capitalAfter downstream of it, then re-runs the end-condition check above — so fixing a misclick can retroactively end a session that looked like it was still running.

trade_manager/session.pyPython
def edit_trade_result(session, idx, new_result) -> dict | None:
    if session["status"] != "active":
        return None
    trades = session["trades"]
    trade = trades[idx - 1]
    if trade["result"] == new_result:
        return None
    trade["result"] = new_result

    for i in range(idx - 1, len(trades)):        # recompute every downstream balance
        t = trades[i]
        before = session["inputs"]["bankroll"] if i == 0 else trades[i - 1]["capitalAfter"]
        t["capitalAfter"] = (
            round2(before + t["stakeUsed"] * (t["payoutPctUsed"] / 100))
            if t["result"] == "win"
            else round2(before - t["stakeUsed"])
        )

    wins = sum(1 for t in trades if t["result"] == "win")
    session["currentCapital"] = trades[-1]["capitalAfter"] if trades else session["inputs"]["bankroll"]
    session["tradesRemaining"] = session["inputs"]["N"] - len(trades)
    session["winsNeeded"] = session["inputs"]["K"] - wins

    reason = check_end_conditions(session)
    return end_session(session, reason) if reason else None
08

Planning a session

Everything above computes one stake at a time once n and k are already decided. This layer's job is landing on a sane n/k in the first place — and it covers two different ways to get there, because "plan today" and "plan toward a future date" are genuinely different problems.

Two building blocks feed both modes: rounding a target win rate to a whole win count, and finding how many trades a balance can actually fund before trade 1's stake drops below a broker's minimum.

trade_manager/masaniello.pyPython
def wins_needed_for_rate(n, win_rate_pct) -> int:
    return min(n, max(1, round((win_rate_pct / 100) * n)))


def compute_max_trades(bankroll, win_rate_pct, avg_payout_pct,
                        diagonal_mode, max_stake_percent,
                        min_stake=1, max_search_n=300) -> dict:
    q = avg_payout_pct / 100
    best_n, best_k = 0, 0

    for n in range(1, max_search_n + 1):
        k = wins_needed_for_rate(n, win_rate_pct)
        table = build_table(n, q)
        stake1 = bankroll * stake_fraction(n, k, q, table, diagonal_mode, max_stake_percent)
        if stake1 >= min_stake - 1e-9:
            best_n, best_k = n, k
        else:
            break                        # first shortfall is the hard ceiling -- see note below

    return {
        "n": best_n, "k": best_k,
        "achievedWinRatePct": (best_k / best_n * 100) if best_n > 0 else 0.0,
        "cappedAtSearchLimit": best_n == max_search_n,
    }

Why it stops at the first shortfall

Because k jumps in discrete steps as n grows, a later n can occasionally clear the minimum stake again even though smaller values in between didn't. "You can plan for 9 trades, just not 7 or 8" isn't a coherent answer to show someone, so the first shortfall is treated as the hard ceiling rather than searching past it for a later reprieve.

Fixed win rate: compute_trade_count_options

Given a starting balance, a target win rate, and an average payout, this scans every trade count from 1 upward and keeps whichever ones that balance can actually afford — specifically, ones where trade 1's stake doesn't fall below a $1 minimum — up to a caller-supplied ceiling (20 by default), returning each as an option with its projected final balance if the plan lands exactly on target.

trade_manager/planning.pyPython
def compute_trade_count_options(bankroll, win_rate_pct, avg_payout_pct,
                                 diagonal_mode, max_stake_percent,
                                 max_options=20, stop_loss=None) -> dict:
    result = compute_max_trades(bankroll, win_rate_pct, avg_payout_pct,
                                 diagonal_mode, max_stake_percent, 1, max_options)
    if result["n"] < 1:
        return {"options": [], "cappedAtSearchLimit": False}

    sl_amount = threshold_amount(bankroll, stop_loss) if stop_loss is not None else None
    q_avg = avg_payout_pct / 100
    options = []
    for n in range(1, result["n"] + 1):
        k = wins_needed_for_rate(n, win_rate_pct)
        table = build_table(n, q_avg)
        projected_final = bankroll * table[n][k]
        profit = projected_final - bankroll
        first_trade_stake = next_stake(bankroll, n, k, q_avg, table, diagonal_mode, max_stake_percent)
        # does losing trade 1 alone cross the Stop Loss threshold?
        survives_first_loss = sl_amount is None or first_trade_stake < sl_amount
        options.append({
            "n": n, "k": k,
            "projectedFinal": projected_final, "profit": profit,
            "profitPct": (profit / bankroll) * 100,
            "firstTradeStake": first_trade_stake,
            "survivesFirstLoss": survives_first_loss,
        })
    return {"options": options, "cappedAtSearchLimit": result["cappedAtSearchLimit"]}

Rather than assume a win rate up front, suggest_best_plan() searches win rates from 1–99% against every affordable trade count and returns the single combination with the highest projected profit that still survives a single first-trade loss without crossing the given Stop Loss. It's a real search, not a shortcut toward the highest number on the grid: a higher assumed win rate always demands a bigger first stake for a fixed trade count, so the Stop Loss genuinely bounds how aggressive a win rate it's willing to suggest. It is degenerate in trade count if left unbounded, though — for a fixed win rate, more trades spreads the same risk thinner while also raising the profit ceiling, so a caller-supplied max_trade_count exists specifically so this can't silently push toward the full 20-trade ceiling on its own.

trade_manager/planning.pyPython
def suggest_best_plan(bankroll, avg_payout_pct, diagonal_mode, max_stake_percent,
                       stop_loss, max_trade_count=20) -> dict | None:
    sl_amount = threshold_amount(bankroll, stop_loss)
    if not (sl_amount > 0):
        return None                     # a zero/negative threshold can never be survived

    best = None
    for i in range(99):                 # win rate 1%..99%, 1% steps
        win_rate_pct = 1.0 + i
        result = compute_trade_count_options(
            bankroll, win_rate_pct, avg_payout_pct, diagonal_mode, max_stake_percent,
            max_options=max_trade_count, stop_loss=stop_loss,
        )
        for opt in result["options"]:
            if not opt["survivesFirstLoss"]:
                continue
            if best is None or opt["profitPct"] > best["profitPct"]:
                best = {**opt, "winRatePct": win_rate_pct}
    return best

Target over time: suggest_multiday_plan_options

Here the question flips: instead of "given a win rate, what can I afford," it's "given a target balance by some future point, what's the safest way to get there." Given a target gain percentage, a count of days available, and a ceiling on total trades, it finds, for every achievable total trade count, the minimum win rate that still reaches the target — the least demanding, safest option for that pace.

Every option is returned, not just one: which trade count versus win rate is an acceptable pace is a tradeoff external to the algorithm, so nothing here picks a single winner the way suggest_best_plan() does — that function has no such external constraint and can settle it on profit and safety alone; this one can't.

trade_manager/planning.pyPython
MAX_MULTIDAY_SEARCH_TRADES = 200        # cost grows ~O(n^3); ~0.23s at 200, ~4.7s at 500

def suggest_multiday_plan_options(bankroll, target_gain_pct, avg_payout_pct,
                                   diagonal_mode, max_stake_percent, stop_loss,
                                   days_available, max_total_trades=20) -> dict:
    capped = max_total_trades > MAX_MULTIDAY_SEARCH_TRADES
    max_total_trades = min(max_total_trades, MAX_MULTIDAY_SEARCH_TRADES)

    target_mult = 1 + target_gain_pct / 100
    q_avg = avg_payout_pct / 100
    sl_amount = threshold_amount(bankroll, stop_loss) if stop_loss is not None else None

    options = []
    for n in range(1, max_total_trades + 1):
        table = build_table(n, q_avg)
        if table[n][n] < target_mult:
            continue                    # unreachable even winning every single trade
        k = next(kk for kk in range(1, n + 1) if table[n][kk] >= target_mult)
        win_rate_pct = k / n * 100
        projected_final = bankroll * table[n][k]
        profit = projected_final - bankroll
        first_trade_stake = next_stake(bankroll, n, k, q_avg, table, diagonal_mode, max_stake_percent)
        survives_first_loss = sl_amount is None or first_trade_stake < sl_amount
        options.append({
            "n": n, "k": k, "winRatePct": win_rate_pct,
            "tradesPerDay": n / days_available,
            "projectedFinal": projected_final, "profit": profit,
            "profitPct": (profit / bankroll) * 100,
            "firstTradeStake": first_trade_stake,
            "survivesFirstLoss": survives_first_loss,
        })
    return {"options": options, "cappedAtSearchLimit": capped}

Relies on build_table(n, q)[n][k] being monotonically non-decreasing in k for fixed n — verified empirically, not just assumed — which is what makes "smallest k that clears the target" well-defined via a plain linear scan.

survivesFirstLoss is a flag, not a filter

Both search functions return every affordable option and let each carry its own survivesFirstLoss value — neither one silently drops the options that would hit Stop Loss on a single first-trade loss. Whether a caller filters those out, flags them, or shows everything is a decision made on top of the results, not inside the search itself.

09

Take Profit & Stop Loss

Independent of the staking math, Take Profit and Stop Loss are a dollar or percentage ceiling and floor watching your actual balance as trades land. Each can be set as percent of your starting bankroll, or a flat dollar figure — and for dollar, exactly what that figure means is deliberately spelled out rather than assumed:

amount

"End once I've gained/lost this much, total, from where I started." The default for both.

floor (Stop Loss only)

"End once my balance drops to this figure" — not once I've lost this figure.

ceiling (Take Profit only)

"End once my balance reaches this figure" — not once I've merely gained this figure.

The distinction exists because it's an easy way to lose real money to a misunderstanding: a $1 stop-loss meant as "stop once my balance is down to $1" ends a session almost instantly if it's computed as the default "amount" mode instead — "stop the moment I've lost $1 total." floor/ceiling exist specifically so that ambiguity can't recur.

Each guardrail also carries its own forceEnd flag (default True) — set to False, check_end_conditions() (§07) simply skips that threshold entirely and the session keeps running past it. The flag only controls whether crossing the threshold ends the session; surfacing any kind of notice about it is left entirely to the caller.

trade_manager/masaniello.pyPython
def threshold_amount(bankroll, tp_sl) -> float:
    # tp_sl = { type: 'percent'|'dollar', value, dollarMode }
    if tp_sl["type"] == "percent":
        return bankroll * (tp_sl["value"] / 100)
    if tp_sl.get("dollarMode") == "floor":
        return max(0.0, bankroll - tp_sl["value"])
    if tp_sl.get("dollarMode") == "ceiling":
        return max(0.0, tp_sl["value"] - bankroll)
    return tp_sl["value"]                   # default 'amount' mode

Why the numbers hold up

None of the math above was designed from scratch here. It's a direct port of a reference implementation that was already hand-tested against a worked example from the original build spec — including the exact $100/3-trade/1-win case walked through in §04 — before a single line of it was translated into this version.

The port carries its own regression suite: 36/36 checks on the core staking math (test_masaniello.py) and 122/122 on the planning search functions (test_planning.py) — including the fully hand-derived edge cases: the diagonal pure-vs-capped split, the exact $1-stop-loss-on-$55-remaining scenario from §09 confirmed fixed, and a case where the live payout differs from the average to confirm the stake actually reacts to it.
